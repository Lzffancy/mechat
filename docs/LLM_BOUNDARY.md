# 代码与模型的边界

一句话：**算得出来的不给模型，判得出来的不给代码。** 越界的两边都出错——代码判语义会
给出无法复现的结论，模型做统计会编数字。

## 分工表

| 环节 | 谁做 | 输入 | 输出 | 越界后果 |
|---|---|---|---|---|
| 解密、导出 | 代码 | 加密库 + 密钥 | JSONL | 模型插不上手，纯计算 |
| 统计、词频、主题命中、网络指标 | 代码 | JSONL | `report_data.json` | 模型算这些必错：48,400 条、41 人、基尼 0.713 这种数它没法保证 |
| 聚类跑数 | 代码 | 词表 | 簇 + 代表消息 | — |
| **簇命名 / 判断哪个簇是垃圾桶** | **模型** | 簇关键词 + 12 条代表消息 | 主题名 + 保留/丢弃 | 用代码按关键词硬拼名字，得到"孩子儿子家长家里女儿"这种名字，等于没命名 |
| **成员画像** | **模型** | 指标表 + 该人 20 条代表发言 | 一段人物卡 | 用代码按阈值打标签，得到"话题发动+长文型"，这不是画像 |
| **关系深挖（单人/双人）** | **模型** | 10~15 个上下文窗口 | 时间线 + 结构判断 | 代码只能算被引率，算不出"她把他听不见关键句解读成不在乎" |
| **报告正文** | **模型** | `report_data.json` + 上一阶段的结论 | HTML / Markdown | 代码套模板出来的是数字罗列，没有取舍 |
| **文案返修** | **模型 + 代码** | 原文 + `prose.check` 结果 | 改写后的句子 | 只靠模型自查会漏，只靠脚本会改出病句，必须两边跑 |

## 三条硬规则

### 1. 正文里的数字只能来自 JSON

模型写"前五人占 53.9%"必须能在 `report_data.json` 的 `meta.top5_share` 找到。发现正文数字
和 JSON 对不上，一律改正文，不改 JSON。出现过的问题：模型把"提及量 15.8%"和"主标签 16.8%"
混着写，读者以为前后矛盾。

### 2. 结论必须带索引

凡是从原文得出的判断，都要指到消息索引（`ctx` 输出的第一列）。这有三个作用：人能复核、
模型自己不容易编、后面改稿知道从哪儿改。反过来，指不到具体消息的"群里普遍认为"一律删。

### 3. 区分三种陈述

- 事实（谁在什么时间说了什么）——可以直接写；
- 统计（多少人、多少条、占比多少）——来自 JSON，标注口径；
- 推断（她其实在试探）——必须带证据，且写成推断（"看起来""按她的说法"），不能写成事实。

模型最常犯的错是把推断写成事实，第二常犯的是把个别人的话写成群体共识。

## 上下文的预算

全量 48,400 条按每条 14 字算约 70 万汉字。整篇塞进去有三个问题：贵、中段遗忘、模型
开始总结而不是读。实测可行的做法：

- 先 `ctx --sample 20` 摸底，人工读一遍，定位到 10~15 个关键时段；
- 每个时段取 40~60 条的窗口，`pad` 给足上下文（引用链、前后语气）；
- 单次调用不超过 120 条消息（约 6,000 字），超了就切块并保留索引；
- 分段结论先落成"事实卡"（带索引的短条目），最后一次成文。直接让模型边读边写长文，
  它会在后半段开始编。

## 模型的选择与设置

| 任务 | 建议 | 理由 |
|---|---|---|
| 簇命名、短分类 | 便宜快的模型，温度 0 | 输出短，判断简单，量大 |
| 人物画像、关系深挖 | 强推理模型，温度 0.3~0.5 | 需要跨窗口保持一致性 |
| 正文写作 | 强模型，温度 0.7，长上下文 | 需要行文节奏和取舍 |
| 文案返修 | 强模型，温度 0 | 只做替换，不要它发挥 |

同一份数据换模型会换结论。要复现，就把模型名、温度、输入窗口一起记在报告末尾。

## 隐私红线

给模型的原文是完整聊天记录，包含第三方的话。三条：

1. 用不保留、不训练的通道；本地能跑就不走云；
2. 只发必要的窗口，不做"全量上传让它自己找"；
3. 产物里保留原话可以，但要加"仅个人参考、不二次传播"的说明，且不公开发布。
