# 分析方法

这里记录的是**固定代码逻辑**——同样的输入必须出同样的数字。凡是需要判断的地方
（簇叫什么名字、这个人是什么角色、这段关系怎么解读），都不在这份文档里，在 `prompts/`。

## 0. 数据流

```
明文 .db ──export_group.py──▶ 群.jsonl ──schema.load──▶ Group(Message[])
                                  │                        │
                                  └── 群_members.csv ──────┘
                                                           │
      ┌──────────────┬──────────────┬────────────────┬─────┴──────┐
   stats.basic    words.Vocab    topics.annotate   netgraph.build  rhythm/profile
      │              │              │                 │              │
      └──────────────┴──────────────┴────────┬────────┴──────────────┘
                                             ▼
                                 report.build_report → report_data.json
                                             │
                                 prompts/ 读其中的数 + ctx 取的原文
                                             ▼
                                     正文（HTML / Markdown）
```

一条铁律：**正文不重算数字**。所有出现在报告里的量，都能在 `report_data.json` 里找到
对应字段。两版报告数字对不上，绝大多数情况是没有守住这条。

## 1. 解析层

`Message` 只保留分析要用的字段：`ts / wxid / sender / type / text / ats / ref_wxid / ref_name`。

- **wxid 为空 = 系统事件**（撤回、拍一拍、入群）。判据用"该行有没有 wxid"，不要用
  `local_type`，因为撤回类 app 消息也带正文，按类型判断会漏。这批数据里 599 条系统消息，
  混进成员榜就会凭空多出一个"人"，而且他还有几百条发言。
- **昵称链**：`remark（备注）> display（群昵称）> nick > wxid 前缀`。都拿不到时回退到
  引用消息里的历史昵称（`refermsg.displayname`），这是唯一能还原改名前的名字的来源。
- **控制字符**：有人把昵称设成 `\x7f\x7f`，必须 strip，strip 完为空就继续往下一级找。
- **同名小号**：同一昵称对应多个 wxid 时，`NameResolver` 按发言量排序加 `(1)(2)` 后缀，
  否则报表里会出现两个一模一样的人。
- **@ 解析**：@ 的文本是"发送那一刻的昵称"，可能被空格截断。依次退化
  精确 → 前缀 → 互为前缀 → 包含（长度≥3），实测命中率约七成，剩下的进 `unresolved`。

## 2. 统计口径

| 量 | 定义 | 为什么这么定 |
|---|---|---|
| 分母 | `len(group.real())` | 系统事件不进分母，否则占比被稀释 |
| 活跃日 | 有真人消息的天数 | 不是自然日跨度，跨度会把沉默期算进来 |
| 会话块 | 相邻间隔 > 30 分钟的切分 | 群聊没有"话题"边界，30 分钟是实测最接近人感的阈值 |
| 集中度 | 发言条数的基尼系数 + top5/top10 份额 | 基尼看整体不均，top5 看头部垄断，两个都要 |
| 平均长度 | 只算有正文的真人消息 | 媒体消息按 0 字算会把均长压掉 |
| 导出缺口 | 月消息量 < 中位数 25% | 必须单列，否则"群冷了"的结论会建在缺失数据上 |

`stats.data_gaps()` 会把这几个月标出来。这批数据里 `2026-04` 只有 192 条，是导出缺口不是沉寂，
所有按月占比的结论都要么剔除该月、要么在正文里注明。

## 3. 分词与词频

`words.Vocab` 三个开关，缺一个榜就不能看：

1. **词性白名单** `n nr ns nt nz vn an eng j jn s l i`。不过滤的话前二十名全是
   "就是/然后/感觉/可以"。
2. **清洗**：先去 URL、长串哈希（≥12 位字母数字）、媒体占位符 `[image]`，再分词。
3. **停用词**：内置一份通用表，但真正管用的是**按群补的**口头禅（"旺柴""红包""好吃"
   "杨院"）。补不补直接决定词频榜有没有信息量。

`distinctive()` 用 `p_u * log(p_u / p_all)` 算每个人的标志性用词，命中数 <8 不参与，
否则一条生僻词能冲到第一。纯词频只会把话最多的人顶上榜，看不到区别。

## 4. 主题：词典是主口径

`topic_lexicon.json` 是 15 个主题 + 关键词 + 权重。三条匹配规则：

1. **长词优先**。否则"吃"会命中"吃亏"、"聊"会命中"无聊"。
2. **英文关键词加词边界** `(?<![A-Za-z0-9])ai(?![A-Za-z0-9])`。不加的话 `ai` 命中
   `wait` / `mail`，实测会让 AI 话题凭空多出两成。
3. **一条消息可多命中**。同时输出两个口径，正文必须写明用的哪个：
   - 提及量（可多命中，加起来 > 100%）：回答"这个话题有多少人参与"；
   - 互斥主标签（取权重最大者，加起来 = 100%）：回答"这个月主要在聊什么"。

覆盖率是关键指标，这批数据约 25%。覆盖率低不是 bug，是短文本的常态，正文里要写清楚
"未命中的 75% 大多是'hhh''+1''几点'这类碎片"，不能拿 25% 的分母去说"职场占 16.8%"。

### 聚类为什么不做主口径

`cluster.py` 是滑窗 TF-IDF + KMeans（连续 40 条有效消息拼一段，步长 20）。它能用，但有三个
固定的坑：

- 一定有几个垃圾桶簇，装的是填充语，任何调参都清不掉；
- 簇的关键词只能提示方向，命名必须看代表消息；
- 对 k 敏感，`sweep()` 的轮廓系数只能用来排除明显不合适的 k（这批数据全在 0.02 上下，
  区分度本来就低）。

所以它的定位是**发现词典漏掉的东西**。这批数据里"彩礼"议题就是聚类先冒出来、词典里没有的。

另外一个必须处理的问题：空文档（纯媒体、全是停用词）的 TF-IDF 向量是零向量，余弦恒为 0，
`argmax` 会把它们全塞进簇 0，制造一个几万条的假簇。`cluster.run()` 里统一标 `-1`。

## 5. 关系网络

### 边怎么定义

| 边 | 来源 | 权重 |
|---|---|---|
| 引用 | `app:quote` 的 `refermsg.chatusr` | 1.0 |
| @ 提及 | 消息正文里解析出的成员 | 1.5 |
| 时序接力 | 60 秒内紧接发言 | 0.15，默认关 |

**不要用时间窗共现当关系边。** 实测 48,400 条按 90 秒邻接能抽出 19,684 条"接力"边，
图稠密化后 Louvain 模块度掉到 0.06 以下，社群发现退化成随机切块。接力只适合解释
"谁紧跟着谁说话"这种语气现象，不适合当结构。

`refermsg.chatusr` 有三种脏数据要过滤：指向群本身（`@chatroom` 结尾）、指向自己、
指向已不存在的 wxid。

### 指标含义

| 指标 | 含义 | 典型误读 |
|---|---|---|
| `pagerank` | 被关注度（被引用越多越高） | 当成"影响力"，其实只反映被回复 |
| `between` | 桥接度，跨圈层中转 | 当成"人缘好"，高介数也可能是被两边拉扯 |
| `reply_ratio` | 被引 /（被引 + 引他人） | >0.5 是被追问型，<0.5 是追问型，不是性格 |
| `kcore` | 核心层编号 | 核心层人多不代表结构紧密 |
| `lift` | `n / (out_a × in_b / total)` | 必须配 `n≥8` 一起看，否则冷门组合霸榜 |

模块度 0.05 意味着**没有派系**，就是一个单层星图。这个结论本身有价值，不要因为数字低就
换算法把它调到 0.4。

### 出图

力导向布局必须**预计算坐标**（`nx.spring_layout`，边长用 `1/w**0.55`），前端用
`layout:'none'`。ECharts 自带的 `layout:'force'` 在 30 节点 / 100 边规模下必然堆成一团并
溢出画布，而且每次刷新位置都不同，图和正文对不上。

## 6. 节奏

- **月度**：消息量 + 活跃人数 + 人均。人均下降但总量不变 = 头部在撑，不是群活。
- **成员流动**：首次/末次发言。判断"人走了"要看最后一条的日期，不能看发言数。
- **接话速度**：`reply_latency()` 只统计 0~600 秒的相邻异人消息，取中位数。均值会被
  "第二天才回"的长尾拉爆。
- **高峰窗口**：`bursts()` 按固定窗口（默认 1 小时）滑动找不重叠的峰值段，比按天更接近
  一次真实事件。这批数据里 2026-06-15 的单小时峰值就是那次相亲复盘。

## 7. 画像

`profile.py` 只出可数的行为指标，不下结论：均长、短句率、表情密度、问句率、情绪词率、
自我指涉率、安慰词率、抽象词率、玩梗率、发起话题次数、时段分布。

`hints()` 给的粗标签（话题发动 / 长文型 / 提问者…）只是给 LLM 的输入提示，**不能直接当
正文结论**。指标能说明"问句率 23%"，说明不了"他在群里负责质疑"。

## 8. 汇总

`report.build_report()` 输出一份 JSON，字段即报告可用的全部素材。`report.write()` 另出
四张表：成员关系指标、主题月度演化、强互动对、成员画像。

正文写作读这份 JSON，配合 `ctx` 导出的原文窗口。数字来自 JSON，判断来自原文，两边不能混。

## 9. 复现清单

换群重跑之前确认这几件事：

1. `data_gaps()` 有没有报月份，有就在正文标注；
2. 主题覆盖率是多少，低于 30% 就别用占比口径讲结论；
3. 系统消息条数对不对（应为 0 进成员榜）；
4. 模块度、基尼系数和图规模是否合理（节点数 ≈ 活跃成员数）；
5. 昵称有没有残留 `wxid_` 前缀，有就是解析失败，先修 `NameResolver`。
